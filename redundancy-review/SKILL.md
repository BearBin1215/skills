# 审查冗余代码及注释

在实现、修改或重构过程中可能残留过时的代码或注释，对后续工作产生干扰，积累技术债。本指南用于发现、评估并清理这些冗余。

## 总则

- 根据用户指定的范围进行审查，没指定时默认审查未提交的 git 改动（`git diff HEAD` 覆盖已暂存与未暂存内容，`git status` 补充新增的未跟踪文件）；仓库未初始化或用户要求时审查全仓。用户只要求审查代码或注释之一时不同时审查另一部分，只说“审查冗余”而未指定范围时默认都审查。
- 本指南示例使用 TypeScript 作为参考，实际工作中务必结合目标语言的最佳实践和社区习惯判断，各语言对导出与可见性的处理差别很大。
- 代码冗余可能来自语义方面考虑，注释冗余可能属于避坑指南。综合判断保留价值，拿不准的问用户，或输出报告时单开一节。
- 本指南只处理冗余问题，逻辑缺陷、安全隐患、性能问题、写作规范等不属于本指南范畴。

## 工作流

1. 读规范，确定项目对注释、导出、命名等方面的既有约定。
2. 结合项目规范和本文档，收集各类冗余。
3. 按照冗余的引入时间（本轮修改/历史残留）、严重程度、冗余类型分档分类。
4. 分析修改方案和建议，注意是否会造成功能回归，方案中应包含风险提示。
5. 输出审查报告，如果用户允许直接修改则动手，需要决策的内容告知用户。

### 分档标准

- 高：会误导后续开发（例如与现状相反的注释），或在发布包中暴露无效 API。
- 中：明确无人使用，删除影响局部。
- 低：可能是出于可读性或语义命名保留，需要与用户确认。

### 需要用户决策的情况

- 引入新依赖有代价，比如增大产物体积、可能产生行为变化。
- 删除影响发布包公开 API，或影响面较大的改动。
- 保留与删除各有理由、需要权衡的情况。

## 代码

### 残留导出

方法、变量通过`export`导出，消费方被删除后，linter 等检查工具可能不会将其判断为死代码。应检查各文件删除了哪些导入语句，根据目标模块所在文件检查是否已经无消费方。

如果仓库作为包发布（或 monorepo 内部包），则需要进一步检查残留的导出是否也供消费方使用。

### 过度封装

- 只有一个消费方、封装起来不会优化可维护性的模块。
- 仅做转发，无实质逻辑的函数：
  ```ts
  function foo(args) {
    return bar(args);
  }
  ```
  仅做极少量简单处理的情况也包含在本类型内。

此类函数可能是为了更好的语义而提取，发现后结合功能和模块分析是否真冗余。在名字没有额外信息时，一般可以内联。

### 近似重复函数

- 对比差异点，确认差异是否对应不同领域、扩展方向或数据约束。
- 观察调用方是否各自成组使用。
- 需要参数分支区分行为时，通常说明语义不同，不要合并。

处置：完全相同 → 合并；语义一致、差异可以参数化 → 抽公共实现；语义不同 → 保留并说明理由。误合并容易引入回归，拿不准时先保留。

### 导入重导出

模块消费方所在位置转移后，可能残留导入重导出：

```ts
export { foo } from "../utils";
```

首先判断是否有意，从设计上可能是承担边界、兼容或聚合等职责。如果不是设计目标，通常不应该保留。如果涉及大量上层模块改动，告知用户影响面。

### 弃用别名与兼容层

为过渡保留的旧名称、旧入口、旧类型，例如 `legacy` 前缀、`v2` 后缀。

- 确认是否仍有消费方依赖旧名称，包括仓库外的消费方。
- 无消费方时删除；仍有消费方时走弃用流程并说明。

### 死分支与功能开关残留

- 功能开关已经固定启用或停用，代码仍按两种状态书写。
- 为兼容旧场景、旧协议保留的降级路径，已经没有对应的使用场景。

判断依据：开关是否还可能取到不同值，旧版本是否仍在支持范围。

### 重复造轮子

- 仓库已有安装类似 lodash / es-toolkit 此类工具库，先检查依赖安装情况，然后检查仓库是否重复实现了工具库已有的逻辑。
- 如果仓库没有安装工具库，结合项目规范分析是否可以引入，告知用户。

### 未使用依赖

- 检查依赖清单（`package.json`、`go.mod`、`cargo.toml` 等）中的依赖是否仍被引用，depcheck、deptry 等工具可以给出线索。
- 删除前确认构建脚本、配置文件、动态加载不会在运行时引用它。

## 注释

### 开发者笔记 / 旧版残留

当前版本显然优于旧版，保留注释没有避免踩坑的价值：

```diff
- 明文传输存在安全问题，改用加密传输
```

```diff
- 甲方案渲染性能差，在XX情况下造成网页卡顿
```

面向过程而非现状的注释：

```diff
- 在输出列表的基础上添加过滤和排序功能
+ 支持过滤、排序功能
```

决策阶段产生的过程性说明（讨论过程、备选方案对比、评审意见）：

```diff
- 组内讨论后决定采用方案 A，方案 B 的对比见 PR #123
```

如果记录的是仍然有效的外部约束，改写为约束说明保留，见"辩护性注释"。

### 与代码不符的注释

- 注释内容与当前代码或行为不符时，以代码为准更新或删除。
- 如果注释描述的是本应成立的行为，先判断是注释过时还是代码缺陷，疑似缺陷列入待确认。

### 辩护性注释

解释“为什么不那样写”的注释，例如性能取舍、平台差异、外部系统的限制。

保留：

- 外部约束仍然有效，后来者很可能踩坑。
- 被否定的是常见写法，因为当前工程的特有限制下不予采用。

删除：

- 原因从代码或测试中可以直接看出。
- 对评审意见的回应。
- 可能踩的坑本身很低级，正常编写都不会采用。

### 复述代码

读一眼相邻代码就能得到的信息：

```diff
- // 将列表按名称排序
  list.sort(byName);
```

```diff
- /** 获取用户名 */
  getName() { return this.name; }
```

### TODO / FIXME 残留

已完成的、没有上下文或没有对应 issue 的待办属于残留，应清理；保留的待办要说明内容或关联 issue，项目有约定时按约定处理。
