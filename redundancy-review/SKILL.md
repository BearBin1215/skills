# 审查冗余代码、注释及周边资产

实现、修改或重构后残留的代码、注释与配套资产会干扰后续工作，积累技术债。本指南用于发现、评估并清理这些冗余。

## 总则

- 范围：用户指定时从其指定；未指定时审查未提交改动（`git diff HEAD` 覆盖已暂存与未暂存，`git status` 补充未跟踪文件）；仓库未初始化或用户要求时审查全仓。只说“审查冗余”时代码和注释都查，只要其中一项时不同时查另一项。
- 对象不限于源码：测试、样式、静态资源、文档与数据层也可能积累冗余，允许时一并检查。
- 本指南示例使用 TypeScript，判断时结合目标语言的最佳实践和社区习惯。
- 只处理冗余；逻辑缺陷、安全隐患、性能问题、写作规范不属本指南范畴。
- 代码冗余可能出于语义考虑，注释冗余可能是避坑指南。拿不准就保留；保留与删除各有理由时交由用户决策。
- 以下情况必须征求用户意见：引入新依赖的代价、删除影响发布包公开 API 或影响面较大、需要权衡取舍的改动。

## 工作流

1. 读项目对注释、导出、命名等方面的既有约定。
2. 收集各类冗余。可借助编译器未使用检查、语言服务、依赖分析工具和引用图缩小范围；工具结果只作线索，逐项人工确认。
3. 按引入时间（本轮修改/历史残留）、严重程度、冗余类型分档。
4. 给出修改方案与风险提示，确认是否会造成功能回归。
5. 用户允许直接修改则动手，需要决策的告知用户。

### 分档标准

- 高：会误导后续开发（如与现状相反的注释），或在发布包中暴露无效 API。
- 中：明确无人使用，删除影响局部。
- 低：可能出于可读性或语义命名而保留，需与用户确认。

### 报告

按类型分组（代码、注释、文档、数据层、静态资源），逐条给出位置、类型、分档与处置建议。仅测试使用的导出、生成代码、涉及外部消费方的改动，以及需要权衡取舍的项单列，避免与普通死代码混在一起。

## 代码

### 导出

- 残留导出：消费方被删后，linter 未必将其判为死代码。按被删的导入语句回溯目标模块，确认已无消费方；仓库作为包发布（含 monorepo 内部包）时，还要确认导出是否供仓库外使用。
- 仅测试使用的导出：源码无消费方、只被测试引用，常见于为单测暴露内部步骤。
  - 并发、回滚、边界规则等难以从公开接口稳定复现的场景，可保留测试入口，但在注释中写明“仅供测试”。
  - 仅覆盖普通行为时，优先通过公开函数测试，收回 `export`，不要当成正常公开 API。

### 模块与路由可达性

- 除符号级导出检查外，从应用入口沿引用图检查文件是否可达；路由、配置、迁移、脚本、测试等按约定加载的文件不能只看引用。
- 删除不可达文件前确认动态导入、框架约定与构建配置；路由页面还要检查链接与导航是否仍有入口。

### 抽象与接口

- 接口形状：可选属性在所有调用点都不传或总传同一个值 → 改为必填或删除，并去掉对应分支；只做转存的别名（`const canDelete = data.canDelete`）直接用原值；拆开再拼回同结构（`{ id: event.id, name: event.name }`）→ 直接传原对象；对内部保证成立的值加可选链或兜底 → 确认不来自外部输入后删除。判断依据是调用点与类型声明，不是函数内部写法。
- 过度封装：只有一个消费方且不改善可维护性的模块；只做转发或极少量处理的函数，名字没有额外信息时一般内联。
- 近似重复函数：差异对应不同领域、扩展方向或数据约束，或调用方各自成组使用时，通常不要合并。完全相同 → 合并；语义一致、差异可参数化 → 抽公共实现；语义不同 → 保留并说明理由。

### 重复的字面量与文案

- 同一组状态、角色、选项文案在多个文件各写一份，先确认语义一致，再抽共享常量。
- 展示场景可能分化：按钮、筛选项、导出标题对同一状态的措辞未必相同，不要强行合并。
- 整段重复的类名可抽组件或常量，抽完保证渲染结果不变；改动文案时检查测试快照、生成图片和页面标题。

### 测试与夹具

- 删除或改变行为时，同步删除只服务旧行为的测试和夹具，避免测试为不存在的路径背书。
- 只被一个测试使用、没有独立语义的夹具可以内联；多个测试共用的工厂保留。
- 过时的快照要更新，不要靠放宽断言让测试继续通过。

### 过渡代码与兼容层

- 残留的导入重导出（`export { foo } from "../utils"`）：先判断是否有意为之（边界、兼容或聚合职责）；非设计目标通常不保留，涉及大量上层改动时告知用户影响面。
- 弃用别名：旧名称、旧入口、旧类型（`legacy` 前缀、`v2` 后缀）。确认仓库内外是否仍有消费方；无则删除，有则走弃用流程并说明。
- 功能开关已固定启用或停用，代码仍按两种状态书写；为旧场景、旧协议保留的降级路径已无对应使用场景。判断依据是开关是否还可能取不同值、旧版本是否仍在支持范围。

### 依赖

- 检查依赖清单（`package.json`、`go.mod`、`Cargo.toml` 等）中的依赖是否仍被引用，depcheck、deptry 等工具可给出线索；删除前确认构建脚本、配置、动态加载不会在运行时引用它。
- 已声明但源码未 import 的，可能是 peer 依赖或版本锁定，先查包管理器的依赖关系再判断，例如测试运行器可能要求直接声明配套的 peer 包。
- 功能重叠的依赖也属冗余，如同时安装两个做同一件事的库。
- 仓库已安装 lodash、es-toolkit 这类工具库时，检查是否重复实现其已有逻辑；未安装时结合项目规范判断能否引入，并告知用户。

### 生成代码与第三方代码

- shadcn 组件、ORM 生成文件、协议生成代码中的未使用导出默认保留，手改会被下次生成覆盖；需要裁剪时改生成配置或在业务层封装。
- 判断文件是否生成，优先看文件头注释、目录约定和项目文档。

## 注释

### 开发者笔记与过程性说明

当前版本显然优于旧版、或只记录过程的注释没有避坑价值，删除：

```diff
- 在输出列表的基础上添加过滤和排序功能
+ 支持过滤、排序功能
```

讨论过程、备选方案对比、评审意见等决策阶段说明同样删除。若记录的是仍然有效的外部约束，改写为约束说明保留，见“辩护性注释”。

### 注释掉的代码

已注释掉的实现、旧参数、调试输出没有保留价值的删除；确有参考价值的改写为说明，或留在提交历史里。

### 与代码不符

- 以代码为准更新或删除。
- 若注释描述的是本应成立的行为，先判断是注释过时还是代码缺陷，疑似缺陷列入待确认。

### 辩护性注释

解释“为什么不那样写”的注释，例如性能取舍、平台差异、外部系统的限制。

保留：外部约束仍然有效，后来者很可能踩坑；被否定的是常见写法，因为当前工程的特有限制不予采用。

删除：原因从代码或测试中可以直接看出；对评审意见的回应；可能踩的坑本身很低级。

### 复述与重复

读一眼相邻代码就能得到的信息：

```diff
- // 将列表按名称排序
  list.sort(byName);
```

同一句解释在多个文件重复出现时，保留一处权威说明，其余引用或省略；各处上下文确实不同时保留并确保同步更新。

### TODO / FIXME

已完成的、没有上下文或对应 issue 的待办属于残留，应清理；保留的待办要说明内容或关联 issue，项目有约定时按约定处理。

## 文档、数据层与静态资源

- 文档：README、开发手册、AGENTS 等可能重复命令、表结构、接口清单；优先保留单一来源，其余用链接。与代码不一致时按“与代码不符”处理；`.env.example`、部署配置等示例也要对照实际读取的配置项清理旧键。
- 数据层：不再读写的列、没有查询使用的索引、被后续迁移抵消的结构变更都是候选项。迁移文件是历史记录，不因当前结构变化删除，检查对象是 schema 与查询；删除列或索引前确认仓库外的消费方、备份与回滚方案。
- 样式与静态资源：未引用的 CSS 变量、工具类、关键帧、图片、字体和图标。删除前检查动态类名、主题配置和构建产物，避免把运行时拼出来的名字当成未使用。
