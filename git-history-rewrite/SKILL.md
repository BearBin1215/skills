# 将最终代码重建为项目演进历史

固定输入提交 SHA 和 tree hash，按最终实现重新安排功能加入顺序。纯历史重写的终态必须与输入 tree 完全一致；实现改进另行处理。

## 阶段划分

从最终可交付能力及依赖设计节点，原历史的文件首次出现顺序仅作参考。节点数量由依赖和审阅范围决定，不固定套用阶段表。

按项目实际情况识别以下关系，无须为不存在的类别补内容：

| 依赖 | 核查内容 |
| --- | --- |
| 源码与类型 | 导入、导出、编译链接、类型推导、动态加载 |
| 调用与装配 | 公共 API、服务调用、命令分发、处理器注册、插件装配 |
| 数据与资源 | 持久化结构、记录或协议格式、生成代码、运行所需资源 |
| 验证环境 | 测试配置、初始化、夹具及其调用的能力 |

这些依赖决定能力最早能在哪个节点成立。编译器通常只覆盖其中一部分，不能据此认定对外调用流程已完整。

- 相互依赖的能力可以同一节点加入；拆得更细时，尚未具备依赖的功能暂不注册或暴露。需要大量改写才能拆开时，调整顺序或合并节点。
- 内部构件可以先行加入，但节点应如实描述已验证的构件，不把仅存在于源码中的功能宣称为完整对外能力。
- 节点计划至少记录完成能力、前置依赖、文件或代码片段归属、装配版本和适用检查，避免重建时临时拼凑来源不明的实现。

## 中间版本

- 从最终代码删去尚未加入的部分，明确完整文件在哪个节点恢复。不复制旧需求或修补过程，也不添加假成功实现来凑节点。
- 测试随真实依赖齐备的最早节点加入。初始化或夹具依赖后续能力时，调整其归属或合并相关节点；不通过跳过测试降低检查要求。
- 骨架尚无实际测试时不凑空测试；跨域测试后移时说明早期覆盖范围。
- 生成文件优先恢复原始 blob；只有中间节点确实需要时才重新生成，并在最终恢复原始结果。
- 业务模块按新增能力增长是合理演进，不能把文件修改或删除一律视为需求反复。

## 逐节点验证

- 检查快照必须只包含该节点的跟踪源码，避免未来文件和旧的增量缓存造成假通过。
- 按节点声明的能力核查调用、装配和资源是否齐备。项目含界面时，再核查其入口、跳转及交互后的后续流程；这不是无界面项目的固定检查项。
- 验证记录绑定实际提交及 tree hash，保留命令、退出码和覆盖范围。相同文件树、检查命令和环境可以复用证据；构建或测试依赖 Git 版本信息时，提交变化也可能影响结果。
- 源码、装配或检查条件变化时，重新验证受影响的快照。所有节点都需要有效记录，不能只验证最新版本。
- 终态使用 tree hash 相等或 `git diff --exit-code` 检查；普通 `git diff` 的默认退出码不能证明内容一致。抽样回放不能替代逐节点有效记录。

## 失败与续跑

检查失败时停在失败节点，判断问题属于缺失依赖、错误归属、装配未完成，还是原实现或环境问题。不要把拆分造成的补救追加成新历史末尾的修复故事。

修正所属节点后重建其后续提交。后续 tree 未变时可保留对应验证证据，变化的快照重新验证。续跑核对计划、已完成 SHA 和快照，不仅依赖提交数量；检查失败但尚未提交的修改不能被当作完成节点。

## 提交时间

- **默认让 Git 记录实际提交时间**，不设置 `GIT_AUTHOR_DATE` 或 `GIT_COMMITTER_DATE` 来回填历史日期；同一秒内的多个提交是正常情况。
- 只有用户明确指定日期范围、原时间点或其他时间策略时才覆盖时间字段，并记录来源。不自行插值、补秒或猜测日期。
- 保留原作者身份；重建、amend、rebase 后核对作者与提交者两个时间字段是否符合所选策略。验证日志使用实际执行时间。

## 可选审计工具

`scripts/audit_history.py` 检查最终 tree、线性父提交及时间策略，不执行构建、测试或入口检查。运行时使用本技能目录下的绝对脚本路径。

默认 `--time-policy actual`；需要验证实际时间范围时传入 `--started-at <开始时间ISO>`。用户明确要求原历史时间时选择 `original-both` 或 `original-author`，不检查时间则选择 `none`。只有用户要求无删除提交时才启用 `--no-deletions`。
